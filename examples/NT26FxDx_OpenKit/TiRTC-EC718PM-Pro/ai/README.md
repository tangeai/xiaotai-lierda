# AI 对话与联系人呼叫

当前功能与云端配置集中在 [AI 呼叫配置篇](../docs/AI呼叫微信与设备配置详解.md)，操作见 [AI 对话](../docs/当前设备操作.md#ai)。AI 发起语音呼叫，通过原有 calls/UI 流程转接。

## 入口与生命周期

- `tirtc_ai_start_service()` 创建 96 KiB、优先级 13 的业务线程；重复启动不创建第二个实例。
- `tirtc_ai_action()` 接受 UI 的开始、停止和导航；0 仅表示受理。
- `tirtc_ai_publish()` 复制 AI 状态和字幕，工作线程自行调用；不要从小栈 GUI 周期调用大快照函数。
- 正式身份、时间、平台 API/MQTT、4G 和 runtime 就绪后才建连。凭据/网络代次变化使原请求失效。
- 获取 AI token、受管 WHIP、发送 `0x2100 start_session`，确认格式后进入对话。后台预备不能占用本应接受 LIVE 的空闲首页。
- 停止后禁止新媒体，发送结束、等待音频和连接安全释放。HOME/CLOCK/MENU/DIAGNOSTICS 可保留 AI；其他页面请求停止。

## 当前音频参数

以下参数对应默认的 `TIRTC_AUDIO_AEC_EN=y`。

| 项目 | 当前值 |
| --- | --- |
| 本机音频 | 16 kHz、单声道 PCM16，20 ms 对应 320 样本、640 字节 |
| 网络音频 | 双向 Opus / 16 kHz 单声道，stream_id 1。上行 20 ms，目标 24 kbit/s，复杂度 3。下行按包解码，单包最长 120 ms |
| 接收缓存上限 | 128 KiB 压缩字节、256 个 Opus 包、81,920 个 PCM 等效样本（5.12 秒），任一上限触发时丢弃新包 |
| 起播缓冲 | 80 ms，短句最多等待 120 ms |
| PCM 单次提交上限 | 首次 3,200 样本（200 ms），持续播放 2,560 样本（160 ms） |
| 播放队列满 | 保留已解码 PCM，间隔 20 ms 重试 |
| 命令槽 | 8 × 4608 字节 |

编解码器在会话准备时创建，停止采播后、交出 RTC owner 前销毁。后台预备连接不提前创建编解码器。对讲模块复用 Opus 实现，各会话持有独立的编解码状态。

AI 默认按半双工处理。回复开始、音频到达或仍有声音待播时，F6D_D 的连续采播保持运行，应用暂停上传麦克风音频。收到回复结束事件并确认播放排空后，立即恢复上传新采集的 20 ms 帧。缺少结束事件时，在队列和播放均排空后，使用距最近语音活动 800 ms 的保护时间。默认构建中，回复期间按一次 KEY2 清除当前回复的待播数据，硬件尾音结束后继续收音。500 ms 内连按两次退出到首页。麦克风开关和音量由 Pro 原界面控制。

云端结束后，设备继续播放待播告别语，待播放排空并保持 1.2 秒安静后退出。播放队列忙时按原节奏重试。连续三次提交返回播放错误，或仍有音频未排空且 3 秒没有播放进展时，报告音频异常并释放会话。用户取消、来电或转入通话依照原会话流程停止。关闭 AEC 时，仍使用原来的普通录放音预热、240 ms 起播缓冲及播放期间上行抑制。硬件约定见 [音频适配](../media/README.md)。

## AI 呼叫接管

标准命令 `device_action/call_contact` 与有效旧式 `call_intent/ai_call_intent` 进入统一处理：校验 → 请求新联系人刷新票据 → 精确唯一匹配 → 返回受理结果 → 排队 calls → 停止 AI → 取得媒体使用权拨号。

不猜联系人，不因为云端说“正在呼叫”就当作已拨出；显式请求视频会返回不支持。取消、来电、断网、解绑使旧请求失效。协议、结果码和示例见主文档，避免在这里重复维护两套配置说明。

## 运行边界

常态保留启动和必要错误，界面中的音频状态与计数继续更新。`[AI-CALL] handoff` 代表已转交通话模块，不代表对端接听。

SDK 的阻塞录音/异步播放退出约束由 media 适配保留，不通过强制删除任务或释放在途缓冲来“快速恢复”。构建、模拟检查和实机效果分别核对，固件用途与构建方式见 [构建与固件](../docs/构建与固件.md)。
