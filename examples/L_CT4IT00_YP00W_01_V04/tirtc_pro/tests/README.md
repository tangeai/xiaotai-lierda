# 多人对讲主机检查

测试不参与固件构建，也不访问平台、串口或设备。需要 Python 3 和主机 C 编译器；后端、协议、音频、设置页、预热及生命周期脚本可直接使用 Zig，房间 UI 与增益脚本可使用 TinyCC 或调用 `zig cc` 的编译器包装。固件仍使用仓库原有 ARM 工具链。

本轮使用 Zig 验证。若给房间 UI 或增益脚本使用 Zig，在工具目录创建 `host-cc.cmd`，内容为 `@"C:\实际工具目录\zig.exe" cc %*`，将它的绝对路径传给 `--cc`；其余脚本可直接传 `zig.exe`。工具和临时可执行文件不加入固件。

| 场景 | 修正后的测试契约 |

## 房间后端

```text
python run_group_backend_test.py --cc <tcc可执行文件路径> --cjson <cJSON.c路径>
```

仓库固件使用 ARM 版 cJSON 静态库，主机测试需另备官方 [cJSON v1.7.16 源码](https://github.com/DaveGamble/cJSON/blob/v1.7.16/cJSON.c)。版本与仓库头文件一致，脚本校验源文件 SHA-256，不下载或替换固件依赖。

测试直接编译实际 `group/tirtc_group.c`、G.711 编解码器和 cJSON；只模拟 HTTP、连接、音频设备、页面快照与时钟。每个场景独立启动进程，避免测试之间残留静态状态。覆盖：

- 创建、加入、退出的 HTTP 200 与业务码校验；前导零房间号和密码。
- 分配版本、身份/路由凭据、会话代际与过期 HTTP 返回。
- 两个信号量、信令注册、两个工作线程分别初始化失败后的重试；保留已创建资源并恢复当前页面意图。
- 控制请求排队、音频预热和提交连接期间发生解绑/重绑时，拒绝使用过期身份或会话凭据。
- 离开页面后再进入时，旧控制请求的迟到结果不能强制跳转页面。
- 入房 ACK 前收发关闭；旧命令和其他房间通知隔离。
- 按住续期、750 ms 未收到本地续期后释放、计时器回绕；录音等待期间松手、重新按下、抢占、超时均丢弃旧录音。
- 16 kHz / 320 样本录音转换为每 20 ms 的 8 kHz / 160 字节 A-law 上行，以及 1、159、160、161、640 字节下行边界、尾样本等待、背压、过期音频，核对实际编码值和完整下行样本序列。
- 来电抢占、音频释放失败时保留连接所有权、断网、页面显示延迟、短来电后恢复与显式退出。
- 全局扬声器与麦克风开关、静音与音量限幅；音量设置 BUSY 保留设置及麦克风通知重试，其他 SDK 设置错误进入安全清理。
- 预热等待时拒绝提前 ACK，只有入房请求发出后的有效确认才能开放收发。
- 快速建连时等待 1200 ms 预计预热尾部再发入房命令；早到/迟到完成通知、时钟回绕、等待期间取消或修改音量、静音入房后恢复与首段音量，以及真正发送入房命令后才开始 ACK 超时计时。

## 下行音频连续性与调度

```text
python run_group_audio_test.py --cc <tcc可执行文件路径> --cjson <cJSON.c路径>
```

此独立检查编译同一生产代码并复用后端模拟，以实际解码 PCM 样本和可控时钟检查 16 个场景：

- 拒绝错误编码、采样率、流 ID 或连接的音频。
- 159 + 1 字节跨包合并后，160 个网络样本扩展为 320 个硬件 PCM 样本，顺序和值保持一致。当前生产代码仍让孤立尾字节等待约 80 ms，但最终复制为两个相同样本，不补零。
- 在提交不忙、无硬件队列积压的模拟条件下，首段软件预缓冲等待 80 ms 或累计 640 字节后批量补充播放队列；这不是入房到喇叭出声的总时延保证。
- 模拟首段附加 80 ms 静音，在正常和抖动到包下只预热一次；估算尾时已过但硬件尚未结束时不重复预热。连接时另有 1200 ms 硬件静音预热，本组未执行其真实 SDK 路径。
- 真正结束后开始新一段语音；短片段累计不足 1 ms 的样本时间；240 ms 播放前瞻边界。
- BUSY 后不重复、不丢失样本；过期尾样本的等待时间不沿用到新样本；退出清空待播数据；时钟回绕。所有接收专用场景保持录音调用为零。

这组回归检查跨包样本连续性、单次队列补充及是否误插入预热；本轮另外用旧实现验证了新增入房等待用例能够检出过早入房。模拟不产生声音，不能替代设备上的音质验收。

### 多人对讲实机音频诊断

当前本地应用通过 `ROOM_AUDIO_DIAGNOSTICS` 观测接收和播放，日志沿用 `[ROOM-AUDIO51]` 标识；Room 音量跟随公共用户设置。开始准备 Room 媒体会话后，每约 5 秒输出两条 `[ROOM-AUDIO51]`，退出时补充最后不足 5 秒的窗口。所有计数均属于当前窗口。

- `rx`：收到的包数、字节数、包长范围；`fmt(s/m/f)` 是 stream/media/flags，优先显示首个错误格式；`bad` 和 `over640` 是格式不符、大包拒收次数。
- `qpeak`：缓存峰值槽数/字节数；队列最多 16 个槽、单包最多 640 字节，总缓存另限 4096 字节。`drop(slot/bytes/age)` 分别表示槽数耗尽、字节容量耗尽和超过 500 ms 的丢包次数。
- `cbgap`：接收间隔最大值；`ts(repeat/back)` 是相邻房间音频时间戳重复/倒退次数，不代表已证实的网络丢包率。
- `play`：`pcm` 为成功提交给音频适配层的 16 kHz 语音样本数（不包含预热静音），不是喇叭实际发声计数；`warm` 为播放段开始时的预热调用次数/附加静音毫秒数，不包含连接阶段 `prewarm_session()` 的 1200 ms；`busy/errors` 为播放提交的忙碌/错误次数。
- `tick(gap/work)`：播放处理的最大调用间隔/最大单次耗时。连续有效 Room 语音每秒约 8000 字节 8 kHz A-law，扩展后 `play pcm` 约为 16000 个 16 kHz PCM 样本；起止静音、队列积压及窗口边界须一并考虑。

实测时仅让电脑连续讲话 20～30 秒，设备不按住讲话，同时保留听感描述。应先确认平台和房间连接正常；只有连接错误时，无法用零收包数据判断播放音质。诊断不打印音频内容或连接凭证，设 `ROOM_AUDIO_DIAGNOSTICS=0` 可关闭。


### 无需进入首页读取信号

原厂固件支持只读命令 `AT+LGETSTATUS?`。115200 波特率下发送后等待完整 JSON 和最后的 `OK`（实机约几秒）；其中 `SignalInfo` 给出 RSSI、SINR、RSRP、RSRQ，不依赖平台或首页。这是原厂已有功能，无需修改或烧录应用。RSSI 为 CSQ 等级，按 `2*n-113` 估算 dBm；RSRP、RSRQ 是 CESQ 索引，按 SDK 文档下界 `n-141` dBm 和 `0.5*n-20` dB 解读；SINR 是 SDK 的 snr 字段，已经是 dB。检查有效范围后再换算，未知值不可当成真实测量。完整返回含设备标识，分享日志时应只保留所需信号字段。
